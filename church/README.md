# 우리교회지원센터 홈페이지 + 관리자 시스템

**우리교회지원센터** (Wori Church Support Center · 약칭 WCSC) — 교회에 필요를 채워주는 곳.
8개 지원 항목 안내, 온라인 신청, 그리고 **로그인 기반 관리자 시스템**을 포함합니다.

- 홈페이지 내용은 **로그인 없이 누구나** 볼 수 있습니다.
- 신청서 제출과 관리자 화면은 **로그인**이 필요합니다.
- 데이터베이스는 **Supabase** (Postgres + Auth + Storage) 를 사용합니다.
  Firebase 로도 그대로 돌아가지만, 지금 운영에 쓰는 것은 Supabase 입니다.
- 설정이 비어 있으면 **로컬 데모 모드**로 동작하므로, 설정 없이도 전체 기능을 바로 확인할 수 있습니다.

## 1. 현재 연결 상태

**Supabase 프로젝트 `tbxosynzszcgtieonsui` 에 연결되어 있습니다.** (`assets/js/supabase-config.js`)

```bash
npm start     # http://localhost:8123
```

실제 데이터가 Supabase(Postgres)에 저장되므로, 로컬에서 테스트한 내용도 운영 데이터에 그대로 들어갑니다.
테스트로 만든 신청·고객은 관리자 화면에서 삭제하세요.

### 어느 백엔드를 쓰는지 고르는 규칙

`assets/js/db.js` 가 **위에서부터 차례로** 확인해 하나를 고릅니다.

| 순서 | 조건 | 동작 |
|------|------|------|
| 1 | `supabase-config.js` 의 `url` · `anonKey` 가 채워져 있음 | **Supabase** (현재 상태) |
| 2 | `firebase-config.js` 의 `apiKey` 가 채워져 있음 | Firebase (옛 백엔드) |
| 3 | 둘 다 비어 있음 | 로컬 데모 모드 |

세 가지 모두 화면 쪽에서는 **똑같은 함수**를 씁니다. 백엔드를 바꿔도 화면 코드는 고치지 않습니다.

### 데모 모드로 되돌리려면

`supabase-config.js` 의 `url` 과 `firebase-config.js` 의 `apiKey` 를 모두 빈 문자열(`''`)로 두면
브라우저 저장소를 쓰는 데모 모드로 돌아갑니다.
이 모드에서는 예시 데이터와 함께 아래 계정으로 로그인해 화면을 둘러볼 수 있습니다.

| 구분 | 계정 | 비밀번호 |
|------|------|----------|
| 최고관리자 (데모 전용) | `admin@caps.or.kr` | `caps1234` |

각 항목 페이지 구조: 필요한 상황 → 지원 내용 → 진행 순서 → 제공 내역·비용 → FAQ → 신청 CTA

### AKC — 어라이즈 코리아 캠프

다른 항목이 제작·중개를 대신하는 일인 것과 달리, **AKC는 직접 기획하고 운영하는 캠프**입니다.
**여름과 겨울**에 열리며, 방식이 두 가지입니다.

| | 방식 | 내용 | 접수 |
|---|---|---|---|
| ① | **등록형** | AKC 수련원(경기 안성)에서 열리는 캠프에 등록해 참석 | AKC 홈페이지 |
| ② | **찾아가는** | AKC 팀이 교회로 가서 그 교회 일정에 맞춰 개최 | 우리교회지원센터 |

캠프 갈래도 둘입니다 — **영성캠프**(청소년 · 청년 · 장년 · 시니어)와
**영역캠프**(물맷돌 수학 · 홈빌더 결혼, 12영역으로 확장 중).

**AKC 공식 홈페이지 바로가기**가 두 곳에 있습니다 — 항목 상세 히어로 옆과 [캠프 종류] 구역 아래.
주소는 `src/data/site.js` 의 `services[5].siteLink` 에 있습니다
(`https://intoedu.github.io/AKC-HOMEPAGE/`, 새 창 · `rel="noopener"`).

내용은 AKC 홈페이지에 공개된 것을 기준으로 썼습니다 — 비전(느헤미야 2:17 · REBUILD),
킹덤 프로듀서/빌더/어라이저, 영성캠프 2박 3일, 물맷돌 4박 5일, 장소(안성), 캠프 이후를 잇는 앱.

> ⚠️ **2026 여름·겨울 캠프의 확정 일정과 참가비는 아직 반영되어 있지 않습니다** (`needsReview: true`).
> 확정되면 `services[5]` 를 갱신해 주세요.

### 항목 갈래 (3가지)

8개를 한 줄로 늘어놓으면 무엇부터 볼지 알기 어려워, 교회가 실제로 겪는 자리를 기준으로 묶었습니다.
`categories` 에 정의하고 각 항목의 `category` 로 잇습니다. 홈 · 센터 소개 · 지원 항목 세 페이지가
모두 이 묶음으로 그려집니다.

이름은 **「-는 교회」로 운을 맞췄습니다** — 세 개가 한 짝으로 읽히도록 한 것이라,
하나만 바꾸면 어색해집니다. 고치실 때는 세 개를 함께 보세요.

| 갈래 | 어떤 자리 | 항목 |
|------|-----------|------|
| **알리는 교회** | 교회를 처음 만나는 자리를 다듬습니다 | 홈페이지 제작 · 디자인 제작 · 스마트처치 앱 |
| **모이는 교회** | 예배와 모임이 이루어지는 자리를 준비합니다 | 교역자 구인 · 음향 세팅 · AKC |
| **세우는 교회** | 사역을 받치는 살림과 공간을 갖춥니다 | 인투오피스 · 부동산 |

새 항목에 `category` 를 빼먹으면 목록 맨 아래 **[그 밖에]** 로 모입니다
(검사 `check-services.js` 가 이 상황을 실패로 잡습니다).

### 항목별 범위 — [이렇게 해 드립니다]

해 드리는 범위를 확인받아 페이지에 반영했습니다. **긍정형 목록 하나로만** 보여 줍니다
(`services[].scope.does` 를 넣으면 상세 페이지에 자동으로 생깁니다).

예전에는 [하는 일 / 하지 않는 일] 을 나란히 두었는데, 홈페이지에서 우리 단점을 크게 늘어놓을
이유가 없어 **없앴습니다.** 꼭 남겨야 하는 것만 `scope.fineprint` 로 **잔글씨 한 줄**만 둡니다.

| 항목 | 어디까지 | 잔글씨 |
|------|----------|--------|
| **디자인 제작** | 시안 제작 · 수정 · 인쇄소에 바로 넘길 파일 | 인쇄비 · 배송비 별도 |
| **음향 세팅** | 전 과정 — 현장 진단 · 장비 선정/구매 · 설치 · 교육 | (없음 — 다 합니다) |
| **교역자 구인** | 조건 정리 → 연결망에서 찾기 → 양쪽 확인 → 연결 | 면접 · 청빙 결정은 교회 몫 |
| **부동산** | 게시판 운영 — 권리 증빙 확인, 게시 · 반려 · 내리기 | **공인중개사법상 중개 아님** |
| **인투오피스** | 전자서명 프로그램 (아래 참고) | 회계 · 문서 · 신고 대행 미포함 |

> ⚠️ **부동산 잔글씨는 지우지 마세요.** 공인중개사법 때문에 남겨 둔 문장입니다 —
> 자랑거리가 아니라 법적으로 분명히 해 두어야 하는 내용이라 잔글씨로 한 번만 적습니다.
> `site.listingBoard.fineprint` 와 부동산 항목의 `scope.fineprint` 두 곳에 있고,
> 검사가 두 곳의 존재를 확인합니다.

> 3만원은 **디자인 제작비**입니다 — 인쇄비 · 배송비는 별도이고, 완성 파일을 받아 교회에서 맡기십니다.
> 부동산 6만원은 **게시판 등록비**이며 중개 수수료가 아닙니다.

### 인투오피스 — 전자서명 (월 6,900원)

## 3. 진입점 — 고객과 직원이 분리되어 있습니다

| 대상 | 진입점 | 하는 일 |
|------|--------|---------|
| **교회 (고객)** | `index.html` 헤더 [로그인] | 지원 신청, 내 신청 조회. 직원 관련 항목은 보이지 않습니다 |
| **센터 직원** | **`staff.html`** | 직원 전용 로그인 · 계정 신청 → 승인되면 `admin.html` 로 자동 이동 |

직원 포털(`staff.html`)은 공개 홈페이지 메뉴에 노출하지 않습니다. 찾아가는 경로는 두 가지입니다.

- 푸터 **센터 안내 → 직원 로그인**
- 홈페이지 로그인 창 하단 **"우리교회지원센터 직원이신가요?"**

### 서로 이동

- 관리자 화면 → 사이드바 맨 아래 **홈페이지 보기**
- 홈페이지 → 로그인한 직원의 사용자 메뉴에 **관리자 화면**
- 직원 포털의 모든 안내 화면에 **홈페이지로 이동** 버튼

### 직원 포털의 로그인 결과별 화면

| 계정 상태 | 화면 |
|-----------|------|
| 승인된 직원 (최고관리자·관리자·직원) | 업무 시스템으로 자동 이동 |
| 승인 대기 직원 | "승인을 기다리고 있습니다" + [승인 확인] 버튼 |
| 고객 계정 | "직원 계정이 아닙니다" + 홈페이지 · 내 신청 내역 안내 |
| 연결 실패 | 원인 안내 + [다시 시도] |

> `staff.html` 에서 하는 회원가입은 **항상 직원 신청**(승인 대기)입니다.
> 홈페이지에서 하는 회원가입은 **항상 고객**입니다. 스스로 직원이 될 수는 없습니다.

### 추가 정보 입력 — 교회명 · 직분 · 연락처는 필수

구글 계정으로 가입하면 이름과 이메일만 넘어옵니다. 그래서 **로그인할 때마다**
교회명 · 직분 · 연락처가 채워져 있는지 확인하고, 비어 있으면 **닫을 수 없는
[추가 정보 입력] 화면**으로 막습니다 (`assets/js/profile.js`).

- **구글 가입 버튼이 회원가입 창 맨 위**에 있습니다 (홈페이지 · 직원 포털 모두).
  아래 입력칸을 비워둔 채 눌러도 되고, 인증 뒤 이 화면에서 받습니다
- 이메일 가입은 지금처럼 폼에서 한 번에 받습니다 (이 화면이 뜨지 않습니다)
- 예전에 만들어진 계정도 다음 로그인 때 이 화면을 거칩니다
- 공개 홈페이지 · 신청 폼 · 직원 포털 · 관리자 화면 **모두** 같은 지점에서 막힙니다
- 배경 클릭 · Esc · 닫기 버튼으로 넘어갈 수 없고, **로그아웃**만 가능합니다
- 저장하면 원래 하려던 동작(신청서 제출, 관리자 화면 진입 등)으로 그대로 이어집니다

> 이 기능은 보안 규칙을 바꾸지 않습니다. 본인 계정의 이름 · 연락처 · 교회 ·
> 직분 수정은 이미 허용되어 있습니다 (직분/승인/권한은 바뀌지 않기 때문입니다).

| **지원 신청** | 신청 목록·검색·필터, 담당자 배정, 마감일, 메모, 할 일, 고객 연결, CSV | `신청·의뢰 관리` |
| **고객 관리** | 교회별 정보, 구독 현황, 신청 이력, 직접 등록, CSV. 교회 정보는 **승인받아야 수정** | `고객·구독 관리` |
| **정보 수정 승인** | 고객에게 보낸 수정 요청과 응답(승인·거절) 현황, CSV | `고객·구독 관리` |
| **구독 관리** | 월 정기 계약 등록(항목·금액·청구일·상태), 월 합계·연 환산 | `고객·구독 관리` |
| **매물 게시판** | 올라온 부동산 매물의 권리 증빙 확인, 게시·반려·내리기, 등록비 확인, CSV | `고객·구독 관리` |
| **정산** | 월별 청구서 자동 생성, 단건 청구 추가, 입금 확인, 미수금·고객별 합계, CSV | `정산 관리` |
| **지원 항목** | **공개 페이지에 나가는 내용을 직접 수정** (아래 참고) | `지원 항목 수정` |
| **관리자 목록** | 직원 승인·거절, 직분 변경, 권한 체크박스, 고객 계정 조회, CSV | `직원 승인·권한 관리` |

| **보안 규칙** | Firestore · Storage 규칙 전체를 한 번에 복사 · 파일 내려받기 · 콘솔 바로 열기 | `센터 설정` |

> **연락처를 새로 찍을 때 주의** — 페이지에 전화·이메일·운영시간·주소를 넣을 때는
> `src/templates.js` 의 `phoneText()` · `emailText()` · `hoursText()` · `addressText()` 를 쓰세요.
> `${site.contact.phone}` 처럼 그냥 찍으면 `data-live` 표시가 없어 **관리자가 바꿔도 그 자리만
> 옛 값이 남습니다.** (하단 안내 띠에서 실제로 났던 문제입니다.)
> `check.js` 가 생성된 HTML을 훑어 표시가 빠진 곳을 잡아 줍니다.

### 4-1. 지원 항목 수정 → 홈페이지 즉시 반영

관리자 화면 → **지원 항목** → 항목별 [수정] 에서 아래를 고칠 수 있습니다.

- 항목 이름, 한 줄 소개, 요약 설명, 소요 기간, 비용 안내
- **지원 내용** (제목 + 설명, 추가/삭제/순서 편집)
- **제공 내역** (목록)
- **자주 묻는 질문** (질문 + 답변)
- **공개 여부** — 끄면 신청 버튼이 막히고 "접수 일시 중지" 안내로 대체됩니다. 페이지 주소는 유지됩니다.

**외부 접수 항목** — `외부 접수 주소` 를 넣으면 그 항목의 신청이 다른 사이트로 연결됩니다.
현재 **홈페이지 제작 · 디자인 제작** 은 @IM 접수 페이지(`koreayjk.github.io/aim/request.html`)로 연결되어 있습니다.

- 항목 상세 페이지의 버튼이 `@IM에서 신청하기` 로 바뀌고 새 창으로 열립니다
- 우리교회지원센터 신청서에서는 체크박스가 아니라 **링크 카드**로 표시됩니다 (선택 불가)
- 주소를 비우면 다시 우리교회지원센터 신청서로 접수합니다

동작 방식은 다음과 같습니다.

1. 정적 HTML(빌드 결과)이 **기본값**으로 먼저 표시됩니다 → 검색 노출과 초기 로딩에 유리
2. `assets/js/live-content.js` 가 관리자 수정본을 가져와 **덮어씁니다**
3. 데이터를 못 가져와도 페이지는 기본 내용으로 정상 동작합니다

수정하지 않은 항목은 기본 내용이 그대로 나갑니다. [기본값으로 되돌리기] 로 언제든 원복됩니다.

> 항목을 **새로 추가**하거나 **순서를 바꾸는 것**은 `src/data/site.js` 를 고친 뒤 `npm run build` 를 실행해야 합니다.
> (항목 개수는 메뉴·목록·비교표 등 여러 곳의 정적 구조와 맞물려 있습니다.)

### 4-2. 작업 관리 (내 작업 · 전체 작업 · 업무량)

**전체 작업**은 권한 없이 모든 직원이 볼 수 있습니다. 누가 무엇을 언제까지 하는지 서로 알 수 있도록 열어둔 화면이며, 수정은 되지 않습니다.

**내 작업**에서는 자기에게 배정된 건만 보이고, 여기서 **마감일(디데이)** 을 직접 설정합니다.
표에서 날짜를 고르면 바로 저장되고 디데이 배지가 갱신됩니다.

| 배지 | 뜻 |
|------|-----|
| `D-7` `D-2` | 남은 일수 (3일 이내면 주황색) |
| `D-DAY` | 오늘 마감 |
| `D+3` | **3일 지남 (지연)** — 빨간색 |
| `미설정` | 마감일을 정하지 않음 |
| `완료` | 완료·취소된 건 (지연 계산 제외) |

**직원별 업무량**은 직원 관리 권한자(최고관리자 포함)만 볼 수 있습니다. 진행 중 건수를 막대로 비교하고, 지연·3일 이내·마감 미설정 건수를 함께 보여줍니다. 담당자가 정해지지 않은 건도 알려줍니다.

> 담당자로 배정된 직원은 `신청·의뢰 관리` 권한이 없어도 **자기 작업의 마감일·상태·메모·할 일만** 수정할 수 있습니다. 담당자 재배정은 권한자만 가능하며, 이 제한은 `firestore.rules` 에서 서버측으로 강제됩니다.

### 4-3. 고객 계정 관리

**관리자 목록 → 고객 계정** 탭에서 가입자 정보를 확인합니다.

| 열 | 내용 |
|----|------|
| 이름 · 이메일 · 연락처 | 가입 시 입력값 |
| **교회** · **직분** | 가입 시 필수로 받습니다 |
| **생년월일** | 가입 시 선택 입력 |
| 가입일 | — |
| **⋯** | 직원으로 전환 / 계정 정보 삭제 |

- **직원으로 전환** — 고객을 직원(승인 완료) 으로 바꾸고 승인된 직원 탭으로 이동합니다. 전환 후 권한 체크박스에서 필요한 항목을 켜주세요.
- **계정 정보 삭제** — `users` 문서를 지웁니다. 그 사람이 남긴 신청 내역은 남습니다.

> ⚠️ 계정 정보를 삭제해도 **로그인 계정 자체는 남습니다.** 브라우저에서 남의 로그인 계정을 지우는 것은 보안상 불가능하기 때문입니다.
> 완전히 지우려면 Firebase 콘솔 **Authentication → Users** 에서도 삭제해 주세요. 지우지 않으면 그 사람이 다시 로그인할 때 고객으로 새로 등록됩니다.

### 4-4. 교회 정보 수정은 그 교회의 승인을 받습니다

교회가 알려준 정보를 센터가 임의로 고칠 수 없게 막아 두었습니다.
**요청 → 고객 승인 → 수정 → 자동 재잠금** 순서로 진행됩니다.

```
관리자: 고객 관리 → 교회 열기 → [정보 수정 요청 보내기]
          ↓  (고칠 항목 선택 + 사유 입력)
고객:  홈페이지 접속 → 안내 띠 · 승인 창 → [승인합니다] / [거절합니다]
          ↓
관리자: 고객 관리 → 잠금 해제 (7일) → 수정 후 [저장] → 다시 잠김
```

**승인이 필요한 항목** (교회가 알려준 정보)

| 항목 | 항목 |
|------|------|
| 교회명 | 담당자 성함 |
| 교단 | 담당자 직분 |
| 소재지 | 연락처 |
| 출석 교인 수 | 이메일 |

**승인 없이 언제든 수정되는 것** — 내부 메모, 구독 계약, 청구·정산, 신청 상태·담당자·마감일

고객 쪽 화면
- 요청이 있으면 홈페이지 헤더 아래에 **안내 띠**가 뜹니다 (모든 공개 페이지)
- 로그인 후 승인 창이 한 번 자동으로 열립니다. **닫을 수 있고**, 띠에서 다시 열 수 있습니다
- 거절할 때 사유를 남길 수 있고, 관리자 화면에 그대로 보입니다

관리자 쪽 화면
- 승인 전에는 해당 칸이 **비활성**이고 `승인 필요` 표시가 붙습니다
- 승인되면 초록색 안내와 기한이 표시되고, 저장하면 곧바로 다시 잠깁니다
- 승인을 안 쓰고 되돌리려면 [승인 반납(다시 잠금)]
- **정보 수정 승인** 화면에서 전체 요청·응답을 봅니다 (대기 건수는 사이드바 숫자로)

> **보안 규칙에도 같은 조건이 들어 있습니다.** 화면의 잠금을 우회해도 Firestore가 거부합니다.
> 직원은 승인 상태를 스스로 `approved` 로 만들 수 없고(`pending`·`canceled`·`used`·`expired` 만 가능),
> 고객은 `status`·`respondedAt`·`expiresAt`·`rejectNote` 만 바꿀 수 있습니다.
>
> 기한(`expiresAt`)은 문자열로 저장되어 규칙에서 비교할 수 없으므로 앱이 확인합니다.
> 기한이 지난 승인으로는 화면에서 수정할 수 없지만, 규칙만 보면 `approved` 로 남아 있습니다.
> 저장을 마치면 `used` 로 바뀌어 규칙 단계에서도 잠깁니다.

> 요청을 보내려면 그 교회에 **연결된 계정**이 있어야 합니다 (`customers.userId`).
> 신청서를 통해 자동 등록된 고객은 이미 연결되어 있고, 직접 등록한 고객은
> [지원 신청] 화면에서 신청 건을 그 고객으로 연결하면 이어집니다.

### 4-5. 내 정보 수정 (고객 · 직원 공용)

로그인한 사람은 누구나 자기 계정 정보를 직접 고칠 수 있습니다 (`assets/js/account.js`).

| 여는 곳 | 대상 |
|---------|------|
| 홈페이지 헤더 → 사용자 메뉴 → **내 정보 수정** | 고객 · 직원 |
| 관리자 화면 → 사이드바 아래 **내 정보 수정** | 직원 |
| 직원 포털 → 승인 대기 화면 → **내 정보 수정** | 승인 대기 중인 직원 |

**고칠 수 있는 것** — 성함, 생년월일, 교회명, 직분, 연락처

**비밀번호 변경** — 이메일로 가입한 계정만 나옵니다. 현재 비밀번호로 다시 인증한 뒤 바꿉니다
(Firebase `reauthenticateWithCredential` → `updatePassword`).
구글로 가입한 계정은 센터에 비밀번호가 없으므로 구글 계정 설정으로 안내합니다.

**바꿀 수 없는 것** — 이메일(로그인 아이디), 직분(역할), 승인 여부, 권한.
뒤 세 가지는 `firestore.rules` 에서 본인 수정이 막혀 있어 화면에도 나오지 않습니다.

> 이 기능은 보안 규칙을 바꾸지 않습니다. 본인 문서의 이름 · 연락처 · 교회 · 직분 수정은
> 이미 허용되어 있었습니다 (role · approved · perms 가 그대로면 통과).

### 4-6. 직분 — 목록에 없으면 직접 입력

직분 선택에서 **기타**를 고르면 직접 입력칸이 나타납니다.
저장되는 값은 입력한 실제 직분 이름이고, "기타"가 그대로 남지 않습니다.
목록에 없는 직분(예: 협동목사)이 저장된 계정을 다시 열면 자동으로 **기타 + 직접 입력**으로 복원됩니다.

목록은 `assets/js/db.js` 의 `ROLE_OPTIONS` 한 곳에 있고, 아래 다섯 화면이 같은 목록을 씁니다.

- 홈페이지 회원가입 · 직원 계정 신청
- 추가 정보 입력(필수) · 내 정보 수정
- 관리자 → 고객 관리의 담당자 직분

### 4-7. 계정과 권한

| 직분 | 설명 |
|------|------|
| **최고관리자** (owner) | 체크 없이 모든 권한. 직원 승인과 권한 부여를 담당합니다. |
| **관리자** (admin) | 체크한 권한만 사용 |
| **직원** (staff) | 체크한 권한만 사용 |
| **고객** (client) | 관리자 화면 접근 불가. 신청과 내 신청 조회만 가능 |

모든 회원가입(고객 · 직원 · 구글 가입)에서 아래를 받습니다.

| 항목 | 필수 | 비고 |
|------|------|------|
| 성함 | ✔ | |
| 생년월일 | | 날짜 선택 |
| **교회명** | ✔ | |
| **직분** | ✔ | 담임목사 / 부목사 / 전도사 / 장로 / 권사 / 집사 / 행정 간사 / 성도 / 기타 |
| **연락처** | ✔ | **숫자 11자리까지만** 입력되고 하이픈이 자동으로 들어갑니다 |
| 이메일 | ✔ | 구글 가입 시 자동 |
| 비밀번호 · **비밀번호 확인** | ✔ | 두 번 입력해 일치 여부를 실시간으로 표시 |

구글 가입도 **교회명 · 직분 · 연락처를 먼저 입력**해야 버튼이 진행됩니다.

- **`staff.html`** 에서 가입하면 `직원 / 승인 대기` 상태가 되고, 관리자 목록의 **승인 대기** 탭에 들어옵니다.
- **홈페이지**에서 가입하면 **고객**으로 즉시 이용 가능합니다.
- **구글 계정으로도 가입·로그인**할 수 있습니다. 로그인 탭과 회원가입 탭 모두에 버튼이 있고, 처음 쓰는 구글 계정은 그 자리에서 자동 가입됩니다. (직원 포털에서 가입하면 직원 신청, 홈페이지에서 가입하면 고객)
  Firebase 콘솔 **Authentication → 로그인 방법 → Google** 을 사용 설정해야 동작합니다.
- 본인 계정의 직분·권한은 스스로 바꿀 수 없습니다 (스스로 잠기거나 승격하는 것을 막습니다).

### 4-8. 부동산 매물 게시판

교회 예배 공간을 내놓는 쪽과 구하는 쪽이 만나는 게시판입니다.
**센터가 하는 일은 게시판 관리뿐입니다** — 중개도, 조건 협의도, 계약 동행도 게시판 서비스에 없습니다.
(그런 도움이 필요하면 `부동산` 지원 항목으로 따로 신청받습니다.)

한눈에: 등록비 **6만원**, 기본 게시 **90일**, 사진 **최대 10장**, 권리 증빙 서류 **필수**,
**연락 가능 시간 필수**, 계좌는 **서류 확인 후 카카오톡으로** 안내.

#### 아무나 올릴 수 없습니다 — 권리 증빙 필수

남의 건물을 아무나 올릴 수 있으면 게시판을 아무도 믿지 못합니다. 그래서 등록할 때
**자신이 이 매물에 대해 어떤 사람인지** 밝히고, 그에 맞는 서류를 첨부해야 합니다.

| 등록자 입장 | 첨부하는 서류 |
|-------------|---------------|
| 소유자 (임대인) | 등기부등본 (부동산 등기사항증명서) · 매매계약서 |
| 임차인 (현재 세입자) | 임대차계약서 |
| 위임받은 대리인 | 위임장 (+ 위임인의 권리 서류) |

- PDF 또는 사진, **10MB 이하**. 형식·용량은 브라우저에서 먼저 걸러지고 `storage.rules` 에서 다시 막힙니다.
- 서류에는 이름 · 주소 · 금액이 들어 있어 **게시판에는 절대 공개되지 않습니다.**
  올린 본인과 승인된 직원만 열 수 있습니다 (`storage.rules` 의 `listing-proofs/{userId}/`).
- 등록자는 네 가지 확인 항목(권리자 확인 / 내용 사실 / 허위 시 삭제·환불 불가 / 센터는 중개하지 않음)에
  모두 동의해야 제출됩니다.

#### 게시글에 들어가는 것

| 항목 | 필수 | 비고 |
|------|------|------|
| 매물 종류 | ✔ | 월세 / 전세 / 매매 / 공간 공유·대여 |
| **주 용도** | ✔ | 교회 · 교육관 · 기도원 · 수양관 · 종교부지 · **기타(직접 입력)** |
| 제목 | ✔ | 최대 60자. **예시 칩**을 눌러 그대로 채운 뒤 고쳐 쓸 수 있습니다 |
| 지역 · 위치 | ✔ | 동 단위까지만 (상세 주소는 받지 않습니다) |
| 면적 · 층 · 주차 · 입주 시기 · 종교시설 사용 | | |
| 금액 | ✔ | 종류에 따라 칸이 바뀝니다. 콤마와 "5,000만원" 표기를 함께 보여 줍니다 |
| **사진** | | **최대 10장** (3장 이상 권장) |
| 상세 설명 | ✔ | |
| 연락받을 성함 · 연락처 | ✔ | 게시판에 공개됩니다 |
| **연락 가능 시간** | ✔ | 보는 사람이 이 시간을 먼저 확인하고 전화하도록 |
| 권리 증빙 서류 | ✔ | 위 표 참고. 게시판에 공개되지 않습니다 |

**제목 예시** (등록 화면에서 눌러 바로 넣을 수 있습니다)

- 뷰가 좋은 3층 예배실 — 한강 조망, 주차 12대
- 지하철 5분 · 주차 8대, 2층 예배 공간 65평
- 리모델링 완료된 교육관 — 소그룹실 3칸
- 단독 건물 전체, 사택 포함 (즉시 입주)
- 상가 1층 · 간판 설치 가능, 유동인구 많은 자리

**사진** — 최대 **10장**, 3장 이상을 권합니다 (예배 공간 전경 / 강단 쪽 / 입구·외관 / 주차장).
올릴 때 브라우저에서 **긴 변 1600px JPEG 로 줄여서** 올리므로 원본을 그대로 고르셔도 됩니다.
첫 장이 목록의 대표 사진이 되고, 순서를 바꾸거나 지울 수 있습니다. 상세 화면은 큰 사진 + 썸네일로 보여 줍니다.

**연락 가능 시간** — 필수입니다. 목록 카드와 상세의 전화 버튼 **위에** 크게 보여 주고,
"위 시간에 맞춰 연락해 주세요 — 등록자가 사역 중일 수 있습니다" 안내를 붙였습니다.
예시 칩도 함께 뒀습니다 (`평일 09:00 – 18:00`, `주일 오후 제외 언제든` 등).

#### 상태 흐름 — 계좌는 승인과 함께 카카오톡으로

```
등록 ──▶ 승인 대기(pending) ──▶ 입금 대기(awaiting_payment) ──▶ 게시중(published) ──▶ 기간 만료
           │  서류 확인 후          │  입금 확인 후                  │
           │  계좌를 카카오톡으로     │                              └──▶ 게시 중지(hidden)
           └──▶ 반려(rejected)  사유가 등록자에게 그대로 보입니다
```

**등록자는 먼저 입금하지 않습니다.** 순서가 이렇습니다.

1. 등록하면 `승인 대기` — 아직 공개되지 않고, 입금 안내도 나가지 않습니다.
2. 관리자가 권리 증빙 서류를 확인하고 승인하면서 **입금 계좌를 카카오톡으로 보냅니다** → `입금 대기`
3. 등록자가 입금하고, 관리자가 확인하면 → `게시중` (기본 90일, 관리자가 7~365일로 조정)
4. 서류가 맞지 않으면 반려 — **계좌 안내를 보내지 않으므로 돈이 먼저 나가는 일이 없습니다.**

계좌는 **등록 화면에 노출하지 않습니다.** 확인되지 않은 글에 입금이 먼저 들어오는 일을 막기 위한 것입니다.
값은 `src/data/site.js` 의 `site.listingBoard.bank` 에 있고, 관리자 화면에서 직원이
**카카오톡 안내문에 담아 복사**해 씁니다 — **아직 예시 값이니 실제 계좌로 교체해야 합니다.**

- 결제는 **계좌이체 후 관리자 확인** 방식입니다 (PG 미연동).
- 등록자가 게시된 글의 내용을 고치면 **다시 `승인 대기` 로 돌아갑니다** (화면과 보안 규칙 양쪽에서).
- 등록자는 상태와 반려 사유를 `listings.html#mine` 에서 봅니다. 직접 삭제도 가능하고,
  삭제하면 첨부 서류와 사진도 함께 지워집니다.

#### 관리자 화면

**게시판 → 매물 게시판.** 필요한 권한은 `고객·구독 관리`(`customers`) 입니다.
사이드바 배지 = **승인 대기 + 입금 대기** 건수 (손이 가야 하는 일의 수).

**1단계 — 서류 확인 · 계좌 안내** (`승인 대기` 글에만 보입니다)

- **권리 증명** 블록에서 [서류 열기 ↗] 로 첨부 파일을 새 창에 엽니다.
  등록자가 적은 연락처와 계정 연락처를 나란히 보여 대조할 수 있게 했습니다.
- 사진 미리보기가 함께 나옵니다 (누르면 원본이 새 창으로 열립니다).
- **카카오톡 안내문**이 미리 채워져 있습니다 — 매물 제목 · 등록비 · 계좌 · 게시 기간.
  [안내문 복사] 또는 [계좌만 복사] 로 복사해 카카오톡에 붙여 보내면 됩니다.
- **[서류 확인 완료 · 계좌 보냈습니다 → 입금 대기]** 를 누르면 상태가 넘어가고,
  등록자 화면에도 "입금해 주세요" 안내가 뜹니다.
- 서류가 맞지 않으면 **[반려]** (사유 필수) — 이때는 계좌 안내를 보내지 않습니다.

**2단계 — 입금 확인 · 게시**

- 입금이 들어왔으면 체크하고 **[게시하기]**. 게시 기간을 7~365일로 조정할 수 있습니다.
- 입금 미확인 상태로도 게시할 수 있지만 확인 창이 뜹니다.
- 게시 후에는 **[게시 기간 다시 설정]** / **[게시 중지]** / **[삭제]** 가 보입니다.
- 기간이 지난 글은 목록을 열 때 `기간 만료` 로 조용히 정리됩니다.

#### 보안 규칙에서 막아 둔 것

`listings` 는 공개 컬렉션이지만 읽기는 **`status == 'published'` 인 글**과 본인 글, 직원으로 제한됩니다.
등록자가 스스로 할 수 없는 것:

- 상태를 `published` 로 올리기 (생성·수정 시 `pending` 만 허용)
- 요금(`fee`)을 납부 처리하기 (`request.resource.data.fee == resource.data.fee`)
- 게시일(`publishedAt`) 채우기 · 남의 글 고치기 (`userId` 고정)

#### 파일 두 종류 — 공개 범위가 정반대입니다

| 경로 | 내용 | 읽기 |
|------|------|------|
| `listing-photos/{uid}/` | 매물 사진 | **누구나** (게시판에 보여 주는 것이 목적) |
| `listing-proofs/{uid}/` | 권리 증빙 서류 | **올린 본인과 승인된 직원만** |

사진은 5MB, 증빙은 10MB 제한입니다. 두 경로를 섞지 않도록 `storage.rules` 에서 따로 막았습니다.

Supabase 에서는 이 두 경로가 **저장소 버킷 두 개**로 만들어집니다 (`supabase.sql` 이 함께 만듭니다).

| 버킷 | 공개 | 용량 제한 |
|------|------|-----------|
| `listing-photos` | 공개 | 5MB |
| `listing-proofs` | 비공개 (10분짜리 서명 링크로만 열림) | 10MB |

> ⚠️ Firebase 로 운영하실 때는 **`storage.rules` 를 따로 게시해야 합니다.**
> Firestore 규칙과 별개입니다 — 관리자 → 보안 규칙 화면의 **[Storage 규칙]** 탭에서 복사하세요.
> Firebase 콘솔에서 **Storage 를 먼저 시작**해 두어야 사진·서류 업로드가 됩니다.

### 4-9. 게시판 세 갈래를 더했습니다 — 중고 장터 · 게스트하우스 · 집회 티켓팅

처음엔 부동산 매물 하나였습니다. **교역자를 돕는다**는 뼈대는 그대로 두되,
물건을 사고파는 일 · 방을 내어 주는 일 · 집회에 신청하는 일은 교역자만의 일이 아니라
성도가 함께 하는 일이라 갈래를 넷으로 나눴습니다.
네 게시판은 모든 페이지 맨 위의 **같은 탭 줄**로 오갑니다.

| 게시판 | 주소 | 등록비 | 센터의 몫 |
|--------|------|--------|-----------|
| 부동산 매물 | `listings.html` | 6만원 | 등록비 |
| 중고 장터 | `market.html` | 없음 | **설치 대행료** |
| 게스트하우스 | `guesthouse.html` | 없음 | (없음 — 게시판만) |
| 집회 티켓팅 | `tickets.html` | 없음 | (없음 — 신청 창구만) |

세 갈래 모두 매물 게시판과 같은 흐름을 씁니다.
등록 → **확인 대기** → (관리자 확인) → **게시** / 반려 / 내리기.
사진은 매물 게시판과 같은 `listing-photos` 버킷을 씁니다(공개 버킷).

#### ② 중고 장터 — 센터가 버는 곳은 물건이 아니라 설치입니다

스피커와 믹서를 중고로 싸게 사도, **예배당에 다는 일은 그대로 남습니다.**
그 일을 센터 음향팀이 맡고 비용을 받습니다. 등록비를 받지 않는 것은 그래서입니다 —
물건이 많이 올라올수록 설치를 부를 일이 늘어납니다.

- 갈래가 **음향 · 마이크 · 영상 · 조명**이면 등록 화면에서 "설치 대행을 안내해도 될까요?"를 묻고,
  글에 **[설치 맡기기]** 버튼이 붙습니다.
- 설치는 세 단계입니다 — 운반만(10만원~) · 설치 · 배선(15만원~) · 설치 + 음향 튜닝(30만원~).
  대수가 늘어도 출장은 한 번이라 **두 번째부터는 절반만** 더합니다.
- 장터 밖에서 구한 장비도 `#install` 로 바로 부르실 수 있습니다.
- 접수된 문의는 관리자 **[설치 대행]** 화면에 대기 건수와 함께 뜨고, 여기에서 견적을 확정합니다.

#### ③ 게스트하우스 — 교회가 내어 주는 방

비어 있는 사택 · 선교관 · 수양관 방을 교회가 내어 놓고,
해외에서 들어와 한국에 머무르는 **선교사 · 방문 교역자 · 유학생**이 빌려 씁니다.
요금은 1박 · 주 · 달 중 쓰는 단위만 채우면 되고, 무료로 내어 주는 방도 그대로 올라갑니다.

> 공중위생관리법상 **숙박업 신고가 필요한 형태인지는 각 교회가 관할 보건소에 확인**해야 합니다.
> 등록 화면의 확인 항목에 그 내용을 넣어 두었습니다.

#### ④ 집회 티켓팅 — 정원이 차면 자동으로 마감됩니다

포스터와 집회 이름을 보고 들어와, 읽고, 신청합니다.

- **예매 시작 시각**(`openAt`)을 정하면 그 전에는 버튼이 열리지 않고 **남은 시간이 1초마다** 줄어듭니다.
  시각이 되면 그 자리에서 정원을 다시 읽어 버튼을 엽니다.
- **정원**이 차면 집회가 `closed` 로 바뀌고 *"정원이 모두 찼습니다 — 마감되었습니다"* 가 뜹니다.
  취소가 나오면 자리가 돌아오고 다시 열립니다.
- **얼리버드** 참가비와 마감 시각을 따로 둘 수 있습니다.
- **좌석도는 선택입니다.** 켜지 않으면 인원수로만 받습니다. 켜면 줄 수 · 줄당 좌석 수로 좌석도를
  만들고, 통로 · 기둥처럼 앉을 수 없는 자리는 눌러서 끕니다.
- 사진은 **최대 20장** — 첫 장이 목록에 보이는 대표 포스터가 됩니다.
- 주최 측은 **[신청자 명단]** 을 화면에서 바로 펼쳐 볼 수 있습니다.

##### 정원은 데이터베이스에서 잠급니다

정원 확인과 자리 차지를 브라우저에서 나눠 하면, 오픈 직후 동시에 눌린 신청이 정원을 넘길 수 있습니다.
그래서 신청은 **데이터베이스 함수 하나**(`public.reserve_tickets`)로 처리합니다 —
집회 행을 `for update` 로 잠근 뒤 정원과 좌석 겹침을 확인하고, 같은 잠금 안에서 신청을 넣고
`taken` 을 올립니다. 취소는 `public.cancel_ticket` 이 반대로 되돌립니다.
`events.taken` 은 트리거(`guard_event_taken`)가 지켜, 주최자가 직접 올릴 수 없습니다.

> Firebase 어댑터와 데모(브라우저 저장소) 모드에는 서버에서 잠글 방법이 없어 같은 순서를 흉내만 냅니다.
> **실제 운영은 Supabase 쪽을 쓰셔야 정원이 지켜집니다.**

`supabase/migrations/20260828010000_wcsc_market_guesthouse_tickets.sql` 에 표와 규칙이 들어 있고,
그 뒤 두 파일이 신청 함수를 다듬습니다.

| 표 | 무엇 |
|----|------|
| `market_items` | 중고 장터 글 |
| `install_requests` | 설치 대행 문의 (공개되지 않습니다 — 본인과 직원만) |
| `guest_houses` | 게스트하우스 글 |
| `events` | 집회 |
| `ticket_orders` | 신청 내역 (`reserve_tickets` 로만 들어갑니다) |

| 마이그레이션 | 무엇을 합니다 |
|--------------|---------------|
| `20260828010000_wcsc_market_guesthouse_tickets` | 표 5개 · RLS · 예약 함수 · 실시간 구독 |
| `20260828020000_wcsc_reserve_closed_message` | 마감된 집회에 신청했을 때 나오는 말을 갈라 줍니다 |
| `20260828030000_wcsc_ticket_taken_guard_fix` | 신청해도 정원이 차지 않던 문제 |
| `20260828040000_wcsc_reserve_duplicate_message` | 두 번 신청했을 때 인덱스 이름이 그대로 나오던 문제 |

> ✅ **세 마이그레이션 모두 운영 프로젝트(`wcsc`)에 적용했습니다.**
> 새 프로젝트에 설치하실 때는 `supabase.sql` 하나만 실행하시면 같은 상태가 됩니다.

> 📌 함께 되찾은 것 — `20260818014534_wcsc_listing_edit_review`
> 매물에 `first_published_at` · `edit_requested_at` 두 칸을 더하는 이 변경은
> **운영 DB 에만 있고 저장소에는 없었습니다** (콘솔에서 바로 실행된 것으로 보입니다).
> 그대로 두면 `supabase.sql` 로 만든 새 프로젝트에서만 이 부분이 빠져,
> 나중에 원인을 찾기 어려운 차이가 됩니다. DB 에서 꺼내 원래 자리에 되돌려 놓았습니다.
> (운영 DB 의 함수 본문과 한 글자도 다르지 않은 것을 확인했으니, 다시 실행하실 필요는 없습니다.)

##### 정원이 차지 않던 문제 (`20260828030000`)

`events.taken` 은 주최자가 손으로 올리지 못하도록 트리거가 지킵니다. 그런데 그 트리거가
**지금 누가 부르고 있는지**를 `current_setting('role')` 로만 판단했습니다. 신청하는 분은
당연히 `authenticated` 이고 직원이 아니므로, `reserve_tickets()` 가 올린 `taken` 까지
되돌려 버렸습니다 — 신청은 들어가는데 정원은 그대로 0 이라 집회가 영영 마감되지 않습니다.
(직원 계정으로 시험하면 `is_staff()` 가 참이라 멀쩡해 보였습니다.)

예약 · 취소 함수가 **트랜잭션 안에서만 사는 표시**(`wcsc.ticket_op`)를 켜 두고,
트리거는 그 표시가 있을 때만 `taken` 변경을 통과시키도록 고쳤습니다.
바깥(PostgREST)에서는 그 표시를 켤 방법이 없습니다.

## 5. Supabase 연결 (현재 운영 백엔드)

`assets/js/supabase-config.js` 의 두 값만 채우면 됩니다. 다른 코드는 고치지 않아도 됩니다.

```js
window.SUPABASE_CONFIG = {
  url: 'https://<프로젝트>.supabase.co',
  anonKey: 'sb_publishable_...',
};
```

### 새 프로젝트에 설치하는 순서

1. [Supabase 대시보드](https://supabase.com/dashboard) 에서 프로젝트 생성 (지역: `Northeast Asia (Seoul)` 권장)
2. **SQL Editor → New query** 에 저장소의 **`supabase.sql` 전체**를 붙여넣고 **[Run]**
   · 표 · 접근 규칙(RLS) · 저장소 버킷 · 가입 트리거가 **한 번에** 만들어집니다
   · 관리자 화면 → **센터 관리 → 보안 규칙 → [Supabase SQL]** 탭에서 그대로 복사할 수 있습니다
3. **Project Settings → API** 에서 `Project URL` 과 `publishable key` 를 복사해 `supabase-config.js` 에 넣기
4. **Authentication → Providers → Email** 사용 설정, **"Confirm email" 은 끄기**
   · 가입하자마자 신청서를 이어서 제출하는 흐름이라, 확인 메일을 기다리면 흐름이 끊깁니다
   · (선택) `Google` 도 함께 켜기
5. **Authentication → URL Configuration** 의 `Site URL` · `Redirect URLs` 에 배포 주소 넣기 (구글 로그인에 필요)
6. 회원가입한 뒤 **첫 최고관리자 지정** — SQL Editor 에서 한 줄:

```sql
update public.users set role = 'owner', approved = true
where email = '본인이메일@example.com';
```

> `anonKey`(publishable) 는 **공개해도 되는 값**입니다. 브라우저에 그대로 나가는 것을 전제로 만들어진 키입니다.
> 실제 접근 제어는 데이터베이스의 **RLS 정책**이 합니다.
> 반대로 `service_role` 키는 RLS 를 통째로 무시하므로 **절대 저장소에 넣지 마세요.**

### 규칙을 고칠 때

`supabase.sql` 은 **직접 고치지 않습니다.** `supabase/migrations/*.sql` 을 고치고 `npm run build` 를 실행하면
파일 이름순으로 이어 붙여 `supabase.sql` 이 다시 만들어집니다. 맨 위 `WCSC_SUPABASE_VERSION` 이 마지막
마이그레이션 번호이므로, 관리자 화면의 `규칙 판` 과 비교하면 무엇이 반영됐는지 알 수 있습니다.

| 파일 | 내용 |
|------|------|
| `..._wcsc_core_tables.sql` | 표 9개 |
| `..._wcsc_security_helpers.sql` | `is_staff()` · `is_owner()` · `can()` · `edit_approved()` |
| `..._wcsc_column_guards.sql` | 열 잠금 트리거 (직분·요금·게시일 등) |
| `..._wcsc_rls_policies.sql` | 접근 규칙 — `firestore.rules` 와 같은 내용 |
| `..._wcsc_storage_buckets.sql` | 사진·증빙 버킷과 그 정책 |
| `..._wcsc_auth_trigger_and_realtime.sql` | 가입 시 `users` 행 생성 · 실시간 반영 |
| `..._wcsc_lock_function_execute.sql` | 함수 호출 권한 정리 |
| `..._wcsc_guards_allow_service_role.sql` | 대시보드·SQL Editor 에서는 열 잠금을 통과 |
| `..._wcsc_tighten_function_grants.sql` | 안 쓰는 함수를 REST 에서 닫기 |

### 왜 정책만으로 안 되고 트리거가 있는지

Postgres 의 `WITH CHECK` 는 **바뀐 뒤의 값만** 봅니다. "요금을 **원래 값에서** 바꾸지 마라" 같은
규칙은 이전 값(`OLD`)을 봐야 하므로 정책으로 쓸 수 없습니다. 그래서 그런 규칙만 `BEFORE UPDATE`
트리거로 따로 두었습니다. Firestore 의 `request.resource.data.fee == resource.data.fee` 와 같은 역할입니다.

### 실제 DB 에서 확인한 것

RLS 정책을 실제 프로젝트에 올린 뒤, 역할별로 흉내 내어 확인했습니다 (확인 후 시험 데이터는 지웠습니다).

| 역할 | 되는 것 | 막히는 것 |
|------|---------|-----------|
| 익명 | 게시된 매물 · 항목 내용 · 센터 설정 읽기 | 고객 · 계정 · 신청서 |
| 고객 | 자기 신청서 · 자기 매물 · 자기 계정, 자기 교회 수정 승인 | 남의 글 수정, 요금 납부 처리, 스스로 게시, 최고관리자 승격 |
| 직원 | 권한(`perms`)이 켜진 화면만 | 스스로 동의 승인, 권한 없는 정산·설정, 스스로 직분 변경 |
| 직원 + 교회 승인 | 그 교회 정보 수정 | — |
| 최고관리자 | 전부 | — |

## 5-1. Firebase 연결 (옛 백엔드 — 그대로 남겨 둡니다)

`assets/js/supabase-config.js` 의 `url` 을 비우고 `assets/js/firebase-config.js` 를 채우면 Firebase 로 돌아갑니다.
다른 코드는 고치지 않아도 됩니다.

1. [Firebase 콘솔](https://console.firebase.google.com) 에서 프로젝트 생성
2. **Authentication** → 시작하기 → `이메일/비밀번호` 사용 설정 (원하면 `Google` 도 함께)
3. **Firestore Database** → 데이터베이스 만들기 (위치: `asia-northeast3` 서울 권장)
4. **Firestore → 규칙** 탭에 규칙 전체를 붙여넣고 게시 (아래 *규칙 게시하기* 참고)
5. **프로젝트 설정 → 내 앱 → 웹(`</>`)** 추가 후, 표시되는 `firebaseConfig` 값을 `firebase-config.js` 에 붙여넣기
6. **Authentication → 설정 → 승인된 도메인** 에 배포 주소(예: `intoedu.github.io`) 추가

### 규칙 게시하기 (전체 덮어쓰기)

보안 규칙은 **부분 수정이 아니라 전체를 덮어쓰는** 방식입니다. 세 가지 방법 중 편한 것을 쓰세요.

#### 방법 1 — 관리자 화면에서 복사 (권장)

관리자 화면 → **센터 관리 → 보안 규칙** (`admin.html#rules`)

1. **[규칙 전체 복사]** 클릭
2. **[Firebase 규칙 화면 열기]** 로 콘솔 열기
3. 편집창에서 `Ctrl+A` → `Delete` → `Ctrl+V`
4. **[게시]**

이 화면에는 배포된 저장소의 `firestore.rules` 가 그대로 표시되므로 **항상 최신본**입니다.
`규칙 판` 번호가 콘솔에 게시한 것과 다르면 다시 붙여넣으면 됩니다.
[파일로 내려받기] 로 `firestore.rules` 파일을 받을 수도 있습니다.

#### 방법 2 — 명령 한 줄 (Firebase CLI)

```bash
npm run rules:login   # 처음 한 번만 (구글 로그인)
npm run rules         # firestore.rules 를 caps-4e079 에 게시
```

`firebase.json` 과 `.firebaserc` 가 저장소에 있어 프로젝트를 따로 지정하지 않아도 됩니다.

#### 방법 3 — GitHub에서 직접 복사

```
raw.githubusercontent.com/intoedu/wcsc/claude/church-support-platform-b296qn/firestore.rules
```

### 첫 최고관리자 만들기

Firebase 연결 후 처음 회원가입한 계정은 승인 대기 상태입니다.
Firestore 콘솔에서 `users` 컬렉션의 해당 문서를 찾아 직접 바꿔주세요.

```
role: "owner"
approved: true
```

이후부터는 그 계정으로 관리자 화면에서 다른 직원을 승인할 수 있습니다.

> `firebaseConfig` 값은 공개되어도 되는 식별자입니다. 비밀 키가 아닙니다.
> 실제 보안은 `firestore.rules` 가 담당합니다 — 규칙을 반드시 게시하세요.

## 6. 신청 흐름

1. 방문자가 항목 페이지에서 **[이 항목 신청하기]** → `apply.html?service=homepage` (해당 항목 자동 선택)
2. 필요한 항목을 **복수 선택** → 선택한 항목에 맞는 추가 질문이 자동으로 나타남
3. 필수값 검증 (교회명 / 담당자 / 연락처 / 소재지 / 요청 내용 / 개인정보 동의), 전화번호 자동 하이픈
4. 제출 시 **로그인/회원가입 모달** → 완료 후 이어서 자동 제출 (입력 내용 유지)
5. `CAPS-YYMMDD-XXXX` 형식 **접수번호** 발급
6. `status.html` 에서 접수번호로 조회, 로그인 시 **내 신청 내역** 목록 표시
7. 관리자 **지원 신청** 화면에서 **[고객으로 연결하기]** 를 누르면 교회명이 같은 고객에 연결되고,
   없으면 고객을 새로 만듭니다 → 이후 구독·정산에서 같은 교회로 묶여 보입니다

> 고객 연결을 신청 시점에 자동으로 하지 않는 이유: 그러려면 신청자가 **다른 교회의 고객 목록까지 읽을 수 있어야** 합니다.
> 개인정보 보호를 위해 조회 권한이 있는 관리자 화면에서 처리합니다.

### 색 배치 — 첫 화면 기준 약 85 : 11 : 4

화면 픽셀을 실제로 세서 맞춘 비율입니다 (뉴트럴 : 브랜드색 : 노랑).
색이 칠해진 면적만 보면 **브랜드색 : 노랑 이 약 3 : 1** 입니다.

**노랑이 나오는 자리** — 헤더 [지원 신청] 버튼, 첫 화면 눈썹 배지, 첫 화면 항목 패널 머리 띠,

통계 띠 위아래 선, 신청서 진행 단계와 고른 항목 칸, 푸터 위쪽 선과 열 제목,
관리자 사이드바 선택 표시.

**배경은 브랜드색·뉴트럴 그대로** — 첫 화면 배경, 번갈아 나오는 구역 배경, 통계 띠 바탕,

노랑이 넓은 면을 덮으면 브랜드색이 사라지기 때문입니다.

## 11. 기술 사항

- 프레임워크·빌드 도구 없음 — 순수 HTML / CSS / 바닐라 JS (생성 스크립트만 Node 사용)
- Supabase SDK 는 저장소에 함께 두고(`assets/vendor/supabase-*.js`) 필요할 때만 불러옵니다 —
  **CDN 을 타지 않으므로** 외부 서비스가 멈춰도 로그인이 막히지 않습니다
- Firebase JS SDK는 필요할 때 CDN에서 동적으로 불러옵니다 (`import()`) — 데모 모드에서는 아예 로드하지 않습니다
- 데이터 계층이 어댑터로 분리되어 있어 백엔드를 갈아끼워도 화면 코드는 그대로입니다 (`assets/js/db.js`).
  실제로 Firebase → Supabase 전환에서 화면 코드는 한 줄도 고치지 않았습니다
- 폰트: Pretendard (CDN), 실패 시 시스템 한글 폰트로 대체
- 반응형: 1180 / 1100 / 1080 / 900 / 820 / 680px 구간. 관리자 화면도 모바일 대응
  (메뉴는 **1100px 이하에서 접힘 메뉴**로 바뀝니다 — 한글 메뉴 6개가 한 줄에 들어가지 않습니다)
- 접근성: 본문 바로가기, 키보드 조작, `aria-*`, 포커스 표시, `prefers-reduced-motion`
- 인쇄 스타일 포함

- 저장하면 Firestore·헤더에 즉시 반영되고 원래 흐름(관리자 화면 진입)으로 이어짐,
  다음 방문 때는 다시 묻지 않음
- 구글 가입 버튼을 빈 칸 상태로 눌러도 사전 입력을 요구하지 않음
- 홈페이지 회원가입 창과 직원 계정 신청 창 **양쪽 모두** 구글 버튼이 폼 맨 위에 위치
- 색 적용 후 공개 페이지 17개(당시) · 신청서 · 항목 상세 · 관리자 화면 · 모바일 재확인 (Pretendard 적용 상태로 렌더)
- 색 비율을 화면 픽셀로 측정 — 첫 화면 뉴트럴 85% · 브랜드 11% · 노랑 4%
- 색 조합 12개 대비 계산 — 최저 4.77:1 로 전부 WCAG AA 이상
- 기획서 3장 가격표 8종이 카드 · 비교표 · 항목 상세에 모두 같은 값으로 표시됨
- AKC 페이지가 캠프 기준으로 재작성되고 참가 대상 · 인원 입력칸이 신청서에 반영됨
- 부동산 · 교역자 구인 페이지에 게시판 준비 중 안내가 들어감 (부동산은 이후 실제 게시판으로 연결)
- AKC 페이지에 캠프 종류 2개 · 갈래 2개가 표시되고, AKC 홈페이지 바로가기가 두 곳에서
  새 창(`rel=noopener`)으로 열림. 신청서에 방식 · 시기 선택칸이 반영됨
- 디자인 · 교역자 구인 · 부동산 페이지에 [이렇게 해 드립니다] 목록이 나오고, 옛 [하지 않는 일] 구역은 사라졌고
  (인쇄/배송 · 공고문/면접 · 중개/용도확인/동행), 옛 문구가 한 곳도 남지 않음
- 음향 페이지에는 범위 구역이 붙지 않고 현장 · 장비 · 설치 · 교육이 그대로 유지됨
- 매물 게시판에서 "계약 전 확인을 함께 짚어 드린다" 는 옛 안내가 사라짐
- 인투오피스 페이지가 전자서명 중심으로 바뀌고, 잔글씨에 회계 · 공문 · 급여 · 4대보험 ·
  인수인계가 모두 적혀 있으며 옛 대행 문구가 한 곳도 남지 않음
- 승인 없이 고객 교회 정보 칸이 비활성이고 `승인 필요` 표시가 붙음, 내부 메모는 그대로 저장됨
- [정보 수정 요청 보내기] → 문서 아이디가 고객 아이디로 저장되고 승인 계정·항목·사유가 정확히 기록됨
- 고객 계정으로 로그인하면 안내 띠와 승인 창이 뜨고, Esc 로 닫아도 띠에서 다시 열림
- 승인 → 관리자 화면에서 칸이 열리고 목록에 [수정 가능] 표시, 저장하면 `used` 로 재잠금
- 거절 → 사유가 저장되고 관리자 화면 잠금 안내에 그대로 표시, 칸은 계속 잠김
- 연결된 계정이 없는 고객에게는 요청 버튼 대신 안내가 표시됨

매물 게시판:

- 비회원에게 **게시된 매물만** 보이고, 승인 대기 · 입금 대기 글의 제목과 증빙 파일 경로가
  목록·상세 어디에도 새어 나오지 않음
- 검색 · 종류 필터 · 지역 필터, 결과 없음 안내
- 비회원이 `#new` 로 바로 들어오면 등록 폼 대신 로그인 안내
- 매물 종류를 바꾸면 금액 칸이 따라 바뀜 (월세 ↔ 매매가 ↔ 전세금), 콤마와 "5,000만원" 안내 표시
- 등록자 입장을 바꾸면 첨부 서류 선택지가 바뀜 (소유자 → 등기부등본 / 세입자 → 임대차계약서)
- **서류 없이 제출 차단**, 확인 항목 4개 미동의 차단, 10MB 초과 파일 차단
- 등록 결과가 `pending` · `fee.paid: false` · `fee.noticeSentAt: ''` · `publishedAt: ''` 로 저장되고,
  증빙 경로가 `listing-proofs/<uid>/…` 로 들어감 → 등록 직후 공개 목록에는 안 보임
- 관리자 사유 없는 반려는 거부, 사유를 적으면 저장되고 **등록자 [내 매물] 화면에 그 사유가 그대로 표시**
- 게시 기간 30일로 게시 → 공개 목록에 나타나고 `expiresAt` 이 30일 뒤로 계산됨
- 게시 중지 → 공개 목록에서 사라짐
- 관리자 [보안 규칙] 화면의 **[Storage 규칙]** 탭에 `listing-proofs` 규칙이 표시됨
- 목록 · 등록 · 내 매물 화면 모바일 가로 스크롤 없음
- 예시 글: 대표 사진 · "사진 4장" 표시 · 연락 가능 시간이 목록 카드에 보이고,
  상세에서 썸네일을 누르면 큰 사진과 번호(3 / 4)가 바뀜
- 용도 필터(교회 / 교육관)가 목록에 반영되고, 용도 '기타'는 직접 입력칸이 열림
- 제목 · 연락 가능 시간 **예시 칩**을 누르면 그대로 채워지고 제목 글자 수가 갱신됨
- 사진 3장 올리기 → 대표 사진 표시 · 순서 바꾸기 · 삭제 반영,
  12장을 한꺼번에 고르면 **10장으로 잘리고** 최대치 안내가 뜸
- 저장된 사진 경로가 `listing-photos/<uid>/…` 이고, 증빙은 `listing-proofs/<uid>/…` 로 분리됨
- 연락 가능 시간을 비우면 등록이 막힘
- **계좌가 등록 폼에 노출되지 않고**, 완료 안내에 "카카오톡으로 보내드립니다 ·
  지금 입금하지 않으셔도 됩니다" 가 표시됨
- 관리자 카카오톡 안내문에 계좌 · 60,000원 · 매물 제목이 들어 있음
- [서류 확인 완료 · 계좌 보냈습니다] → `입금 대기` 로 넘어가고 `fee.noticeSentAt` 기록,
  입금 확인으로는 표시되지 않으며 게시일도 비어 있음
- **입금 대기 글도 공개 목록에 보이지 않음**
- 등록자 [내 매물] 에 "입금해 주세요 · 계좌는 카카오톡으로 보내드렸습니다" 표시
- 입금 대기 필터에서 열면 1단계 버튼이 사라지고, 입금 확인 후 게시 → 공개 목록에 나타남
- `storage.rules` 에서 사진은 `allow read: if true`, 증빙은 공개 읽기가 **없음**
- 메뉴 항목이 6개로 늘어난 뒤: 1180 / 1280 / 1440px 에서 한 줄 유지, 1100px 이하에서는 접힘 메뉴로 전환
- `firestore.rules` 에 승인 검사, 고객이 바꿀 수 있는 항목 제한, 직원의 자가 승인 차단이 모두 포함됨
